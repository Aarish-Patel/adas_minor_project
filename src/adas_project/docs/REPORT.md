# Intent-aware ADAS for a 1:14-scale electric car - project report

*Living document. Updated at session ends and at milestones (last update: 29 Sep 2026, afternoon). Every number below was
produced by code in this repository; where something was not measured on the real car, it says so.*

## 1. What was built

A driver-assistance system for a small radio-controlled car (Raspberry Pi 5, RPLIDAR, ESP32 motor/servo controller, optionally
a rear webcam) that is meant to behave like the ADAS in a production electric vehicle - not like a robot that drives itself.
The human keeps the throttle and the wheel. The system watches the world (LiDAR scans, scan-matched motion), predicts where
the car is going, estimates what the *driver* is about to do, and only takes control when a collision is really coming. When
it does, it uses the least intervention that keeps the car safe: a slower throttle, a small steering nudge, an evasive
manoeuvre round the obstacle, or, last, a brake.

What runs on the car (`pi/`) and on the laptop (`gui/`, `sim/`) is the same code (`adas/`, `pi/relay_assists.py`):
the laptop digital twin drives the car's actual relay code against a simulated LiDAR and vehicle, so every result below can
be re-run without hardware.

| Layer | What it does | Main files |
|---|---|---|
| Perception | LiDAR scan filtering, obstacle memory, moving-object tracks, ICP scan-matched pose, rear-camera vision | `pi/relay_assists.py`, `adas/tracking.py`, `adas/vision/` |
| Prediction | swept path at the current steering, driver-intent risk (gradient-boosted trees) | `adas/intent_net.py`, `pi/path_gate.py` |
| Planning | Hybrid A* with Dubins/reversing legs, crossing planner for moving objects, MPPI fallback | `adas/hybrid_astar.py`, `adas/dubins.py`, `adas/crossing.py` |
| Control / safety | path-predicted brake gate (least-restrictive filter), evasive steer, steering nudge, corridor centring, speed-limit zones, throttle smoother, realistic steering envelope, drive modes | `pi/path_gate.py`, `adas/assists.py`, `pi/zones.py` |
| Supervision | health monitor (normal / limp / fault), supervised ESP32 link, failsafes | `pi/health.py`, `pi/esp_link.py` |
| HMI | EV-style Qt GUI, 3D scene, drawers, Monte Carlo and ML training labs | `gui/` |
| Verification | digital twin, 20 scenarios, randomised repeatability, Monte Carlo, fault injection, log replay, 125 unit tests | `sim/`, `tools/replay_log.py`, `tests/` |

## 2. Methods, and the published work each one is based on

Full derivations and the reasons for each choice are in `RESEARCH.md`; this is the map.

1. **Path planning - Hybrid A\*** (Dolgov et al., IJRR 2010) with **Dubins** analytic expansion (Dubins 1957) for goal poses,
   forward-first search with a 7x cost on reversing, coarse lattice for goals with a required heading, loops over 270 deg refused.
   Incremental re-planning from the current pose when new scans invalidate the path. MPPI (Williams et al., T-RO 2018) as local fallback.
2. **Safety filter for the brake and nudge** - the gate acts only on what the car can still change before its next decision
   (least-restrictive filter: Hsu, Hu & Fisac 2024; Wabersich & Zeilinger 2021; control barrier functions, Ames et al.), using a
   composite swept path built from recent steering commands, with fitted actuation delay and speed-dependent protective fields (ISO 3691-4 practice).
3. **Localisation for speed and turn rate** - keyframed ICP scan matching replaced RF2O odometry (yaw-rate bias +1.4 deg/s) and a wheel-speed proxy; drift 1.6-1.8 %.
4. **Driver-intent model** - gradient-boosted trees trained on data generated by a **domain-randomised digital twin**
   (Tobin et al. 2017; Peng et al. 2018; SimOpt / BayesSim for the real-to-sim loop; Feng et al. 2021 for scenario over-sampling
   of dangerous moments). Held-out average precision 0.42 -> 0.86. Ablation: trained with randomisation vs on the nominal twin, tested on unseen wider cars: AP 0.85 vs 0.63.
5. **Moving obstacles** - crossing planner in path-velocity (s-t) space (Kant & Zucker 1986; Fraichard) choosing clear / pass / yield / wait / stop / away.
6. **Realistic steering** - kinematic (Ackermann) limit with a speed-dependent lateral-acceleration cap scaled to 1:14 (`KAPPA_REAL`, 0.6 g equivalent); online steering calibration by recursive least squares on scan-matched yaw per distance.
7. **Speed-limit zones** - polygon/circle/rectangle zones in the world frame, km/h scaled 1:14, look-ahead 0.5 s.
8. **Formal safe distance** - Responsibility-Sensitive Safety (Shalev-Shwartz, Shammah, Shashua 2017) as an independent yardstick shown in the HMI (`adas/rss.py`).
9. **Rear camera vision** - ground-plane inverse perspective mapping visual odometry, plane+parallax residual blobs with looming time-to-contact (Lee 1976 tau), image-quality and camera-measured vibration (Laplacian variance, phase correlation - Kuglin & Hines 1975), LiDAR-camera late fusion, reversing guidelines, the **ghost car** (swept-body prediction) and a floor-patch warning.
10. **HMI design** - HarmonyOS-style palette (Night Black / Snow Gray / Cosmic Blue used for lines, never flat fills), DIN-style typography, tile-grid settings as in production cockpits; visualisation elements from Tesla's FSD display reference; NHTSA L2/L3 human-factors guidance for glance time and staged warnings.

## 3. Problems faced and how they were solved

| Problem seen | Cause found | Fix | Evidence |
|---|---|---|---|
| Evasive steer got stuck at full throttle | driver's full-speed input predicted a crash a slower speed would avoid | the assist tries a reduced speed first, then plans; stalls re-plan 3x, then back off | `tests/test_planning_safety.py` StuckRecoveryTests |
| Car kept reversing / path disappeared after a reversing leg | tracker ignored the cusp at the end of a reversing leg | `past_cusp` in both trackers | scenario "reverse leg" |
| Car jerked forward/reverse when re-planning | commands switched instantly | `ThrottleSmoother` (rise 600/s, fall 1500/s, reversal drops to zero, safety cuts bypass) | replay of the real 22:11 log: reverse-brake pulses 53 -> 3 |
| "Still not working" on the car after the planner looked fine in simulation | planners could not see the gate's hidden blind-ring memory points | planners now receive the gate memory's blind points | on-car retest pending |
| Brake hammering in a real log | closing-speed noise, latch release mid-pulse | closing speed only for tracker-flagged moving objects, release only after the pulse, softer pulse, reverse lockout | 21:24 log replay: brake pulses 252 -> 103, holding 1471 -> 317 |
| Monte Carlo counted the smoother as an intervention (~400 phantom needless brakes) | classification after smoothing | classify before smoothing | needless brakes ~0 |
| Crossing planner flipped on noisy tracks | 20 mm noise made static objects "move" | tracks need >= 5 moving samples and 0.15-2 m/s; swerve held 1.4 s | `tests/test_crossing.py` |
| Yaw estimate wrong | RF2O bias, EKF dominated by its model | estimate steering calibration from the scan-matched pose | `tests/test_online_steering.py` |
| Intent model poor in general (user: "not just the wall case") | trained on one nominal twin | domain randomisation + feature set v3 + trees | AP 0.42 -> 0.86; ablation table in RESEARCH.md |
| Trees exported from sklearn disagreed with the car's copy | fitted on float32, evaluated in float64 | car copy casts to float32 | 14/400 ticks previously took the other branch |
| ESP32 not responding | dead chip; USB flakiness | replaced board, supervised link with PING/reboot detection | `tests/test_esp_link.py` |
| Vision on the synthetic camera | non-periodic floor seam, mask-edge features, weak parallax, 180-deg ambiguity | erode mask, longer baseline, try both board orientations | `tests/test_vision.py` |
| GUI drawer clipped at full screen; pressing Rear camera hid the bottom bar | drawer contents forced a minimum size larger than the screen | scrolling drawers with wrapping text, bars that never widen the window, size clamped to the screen | `tests/test_gui_smoke.py` (1100x700, 1366x768, 1920x1080) |

## 4. Results (digital twin; the car was not available for new runs)

- **Scenarios:** 20/20 pass on the relay code (wall, box, doorway, reversing, corridor, moving obstacles, fault cases).
- **Repeatability on randomised twins** (20 draws x 15 scenarios): 100 % safe (no contact), 90.7 % meet the nominal spec. The steering nudge is the weak assist at 55 % (fails when the servo-centre error drifts the car toward the 3 cm clip box) - a known limitation.
- **Monte Carlo, four systems, same drives** (12 seeds x 3 driver styles = 36 paired drives, `models/mc_live`): driver only 3 crashes; brake only, ADAS and ADAS + intent 0 crashes. Needless interventions: brake only 43, ADAS 69, **ADAS + intent 45**; needless takeovers 58 -> 25 with intent (paired Wilcoxon p = 0.001). The earlier 96-drive comparison of ADAS vs ADAS + intent gave 123 -> 84 needless interventions.
- **Fault injection:** LiDAR dropout, frozen scan, 30 % command loss and spurious points are all safe. Scan latency: safe up to ~0.1 s extra at full throttle; contact from ~0.15 s (the car would need online latency estimation - open).
- **Real-log replay** (identical recorded scans through the current code): see section 3 for reverse-brake and hold reductions.
- **Vision (synthetic camera with ground truth):** visual odometry within 0.5 % speed / 1 % yaw; pipeline 3.6 ms/frame on the laptop (~13 ms Pi estimate); calibration recovers height/pitch/yaw.

## 5. Why this is different from what is on the market

Production ADAS (Tesla, Huawei ADS, XPeng XNGP, Mobileye) are built for full-size cars with cameras, radars and neural perception; the
published small-vehicle work is mostly either a fully autonomous robot or a single-function demo. What this project does that is
uncommon, and can be defended with the evidence above:

1. **Driver-intent-aware intervention on a small platform.** The system estimates whether the *driver* is about to do the safe thing and withholds intervention when they are, cutting needless takeovers by more than half while staying at zero crashes - measured on paired drives, not asserted.
2. **A digital twin used as the training and test bench, with domain randomisation and a randomisation ablation** - the same code that runs on the car is trained, tested and stress-tested (faults, repeatability, Monte Carlo) before it touches hardware, and real logs are replayed through it.
3. **Least-restrictive shared control**, with a full escalation ladder (nudge -> speed limit -> evasive manoeuvre -> brake) and formal cross-checks (RSS), so that the system is measurably *less* intrusive than a plain brake-only assist.
4. **Full-size behaviour scaled down:** speed-dependent steering limits, km/h speed zones and a drive-mode system at 1:14, with the human-factors HMI conventions of production cockpits.
5. **Honest verification:** unit tests (125), repeatability, fault injection, replay of real logs, and a written list of what is *not* verified on the car.

## 6. Limitations and what is not verified

- The latest code (drivetrain protection, moving-obstacle assist, vision, EV GUI, drive modes) is **not yet deployed to the Pi**; the last on-car test was the 22:15 deploy on 28 Sep. The rear shaft of the car is broken, so no on-car results exist after that.
- The rear camera code is tested against a synthetic camera only; no real webcam has been connected. The floor-patch (puddle) warning is a brightness/texture heuristic, not a learned detector.
- Scan latency above ~0.15 s defeats the gate at full throttle (see section 4).
- The steering nudge is unreliable when the servo centre is mis-set (55 % in the randomised test).
- HarmonyOS status colours (red, orange, green) were taken from memory, not from the official spec; Huawei's exact ADS screens are not public, so the HMI follows the documented Tesla/generic patterns plus the HarmonyOS palette.
- Calibrations (LiDAR offset, servo centre, braking) were deliberately not re-run; they happen only when requested.

## 7. Reproducing

```
python -m unittest discover -s tests            # 125 tests
python -m sim.relay_scenarios                   # 20 scenarios on the relay code
python -m sim.repeat_scenarios                  # randomised repeatability
python -m sim.relay_mc --live 12 off,brake-only,adas,adas+intent lapsing,aggressive,late   # Monte Carlo for the lab
python -m gui.dashboard --open mc               # research consoles: mc, train
python tools/replay_log.py <drive log>          # real log through the current code
```
